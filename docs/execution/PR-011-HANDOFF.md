## Behavior and compatibility

The new `omniweft_contention` host shares the existing policy owner under explicit `policy.retry.v1`. A fixed four-entry per-principal receipt window uses canonical typed-envelope equality, absolute 2,000 ms expiry and an admission high-water mark. Exact retained requests reuse the original volatile receipt; changed payloads return IDEMPOTENCY_MISMATCH; expired, compacted or consumed-without-receipt keys require resync. Host metadata is bounded separately from existing policy world quotas. Current authentication, epoch and live lease checks precede replay. Receipt moves precede response serialization; uncertain responses cannot cause reapplication.

New `RetryPolicySession`/`RetryPolicyClient` classes negotiate strict opt-in capabilities. Immutable prepared requests bind to their creating client; explicit retries preserve their exact key and payload. Reads do not clear pending uncertainty, and fresh requests require explicit reconciliation first. Convenience transact callers must resync on uncertainty unless they used prepare/submit and retained the handle. Legacy hosts/clients remain resync_only. No grants, quota, lease, dependency, save-format or persistence change is introduced; no GPU/physics or crash-safe exactly-once claim is made.

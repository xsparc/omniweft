# FP-008 asset retention inspector

Authorized by the maintainer's [2026-10-07 adoption](FEATURE-IMPLEMENTATION.md). Branch `codex/fp-008-retention-inspector` starts at verified PR #29 merge `2afd15d1cc827389e084bc9c8223f49a7148aded`. PR-016 is integrated; the original 38 ledger items remain unchanged.

Add one const native query, `Catalog::inspect_retention(expected_revision)`. It returns the observed revision, status/code and an optional version-1 detached report. Success is `ok`; a mismatched revision returns `rejected/REVISION_CONFLICT` with no report. Allocation failure returns `rejected/RESOURCE_EXHAUSTED` with no partial report. Querying never advances revision or changes roots, manifests, content or export bytes. The caller still serializes Catalog access; an expected revision is scoped to that live Catalog instance, not a cross-Catalog identity token.

The report enumerates sorted current roots and named history sets, including empty sets; each asset identity links its content hash and exact current/history reasons. Each blob lists all referencing manifest identities separately from the subset that retain it. Removal candidates are every unrooted manifest and every blob with no rooted referring manifest. Eight manifests, eight blobs, four history sets and eight references per root set bound the result. No content bytes or provenance strings are copied into the inspector. Keep the existing `Collect` algorithm and all mutation commands unchanged.

The seed-7 `assets.explain_retention` example uses two provenance-distinct manifests sharing content plus an independent blob. Multiple root reasons and empty sets demonstrate exact explanations. Removing one reason preserves the others; stale queries reject and a fresh query recovers. Reconstruct a fresh private Catalog through ordinary Import and explicit root commands, then compare actual before/after collection identities with predicted removal sets. Reconstruction has its own revision; do not clone Catalog or restore authority metadata. Verify detached report mutation cannot affect its source and that dropping the final root changes the blob candidate set.

The independent Python oracle derives literal fixture identities, full states and expected explanations, and checks exact types, fields, revisions and removal sets. Corruption selftests reject changed root reasons, hidden shared retainers, asset/blob confusion, false removal candidates and false read-only claims. Native boundary checks exercise empty catalogs, all rooted/unrooted content, eight shared provenance variants, eight distinct blobs, four full history sets, sorting, detachment and failed mutation recovery.

This is a CPU-only native diagnostic. No remote endpoint, SDK profile, new grant, World reference inference, automatic undo roots, graph dependency policy, durable store, dependency or save-format change; no GPU or physics claim. Rollback removes the additive query/example through a PR without changing existing bundles or collection behavior.

The coordinator owns the ledger, integration, CI and documentation. An isolated helper owns the additive Catalog API/implementation/native tests; another owns example/oracle sources. Independent architecture review found no blocker. Independent source, oracle, CI and evidence archive reviews are required before draft delivery. Run pinned Windows tests, exact-source clean evidence and hosted Windows/Linux checks, verifying both hosted manifests and their source/artifact bindings. Keep artifacts synthetic and sanitized, with no raw process output or executable bytes.

Focused research on 2026-10-07 reviewed the [Nix garbage-collection diagnostic contract](https://nix.dev/manual/nix/2.30/command-ref/nix-store/gc), which distinguishes root/live/dead inspection from collection. This is advisory motivation for an explainable diagnostic, not a dependency selection or a claim of compatibility. Omniweft's existing two-level manifest/blob retention rules determine the implementation. The explicit maintainer instruction, not this research, adopts the feature.
